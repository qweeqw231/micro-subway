## 0. 结论

**MVP 一句话：** 在 1280×800 的原创抽象城市轮廓上，玩家用 2–6 条彩色线路连接 6–17 个站点，乘客按“最少换乘 / 最短广义时间”自动寻路换乘；每周获得一次二选一升级（部分周为三选一），任何站点队列超过容量并累计到宽限（基础 18 秒）即失败；三张手工地图、鼠标与触控双操作、本地三槽位存档并支持 JSON 文件导出/导入。Web 版达到验收门槛后，仅替换平台适配层，用 Tauri 2 打包 Windows 桌面版。

| 关键决策 | 结论 | 理由 |
|---|---|---|
| 线路编辑成本 | 只花“施工时间”，不引入货币 | 保持 Mini Metro 式流畅改线，同时让改线有代价；避免双资源导致新手算不过来 |
| 寻路目标 | 目标是“站点类型”，不是某一个具体站 | 同类型任一站均可到达，避免“唯一目标站不可达”造成的不可理解卡死 |
| 失败条件 | 仅站点队列超载，不设总运力/资金破产 | 失败原因可定位到具体站点，复盘清楚 |
| 周经济 | 每周 1 次升级卡选择，无金币 | 单资源决策，节奏清晰，便于平衡 |
| 平台路线 | Web 优先，成熟后 Tauri 2 桌面 | 代码复用高、安装包小；桌面端只换适配层 |
| 存档 | 本地 3 槽 + JSON v1 导出/导入，无账号无云 | 直接解决“换设备丢档”；Web 与桌面共用同一 Schema |
| 内容规模 | MVP 三张地图、4 种站点、6 条线、7 类升级 | 三图数据驱动，新增成本低；先保证核心循环完整 |

**MVP 不做：** 账号、云同步、排行榜、联机、每日挑战、无尽模式、地图编辑器、轮渡、环线、线路中段插站、成就、付费。桥隧以“额度”形式实现，不是货币费用。

## 1. 产品定位与设计目标

### 1.1 定位

- 类型：单机、实时、轻策略的公共交通线路规划游戏。
- 单局目标时长：15–25 分钟；首次失败中位周数目标为 6–9 周（标准图）。
- 胜负：MVP 采用无尽生存，不设固定胜利条件；单局以失败结束，记录本局存活周数与送达数，标题页展示本机最佳周数。P1 再加入每图目标与奖牌。
- 受众：玩过同类玩法、想随时打开就玩、不想被账号和联网束缚的玩家。
- 商业模式：个人非商业作品；若公开发布，优先免费静态网页 + 可选桌面安装包。
- 情绪关键词：秩序、清晰、可恢复、轻压力。

### 1.2 设计支柱

1. **一眼看懂**：站点形状 = 乘客目的地类型；线路颜色 = 线路身份；队列、列车满载、施工、超载都必须有直接视觉反馈。
2. **失败可解释**：失败时必须能指出“哪个站、因为什么、哪条线没跟上”，并提供本周快照重试。
3. **改线是主要操作**：玩家 70% 的时间在画线、改线、观察队列，而不是点菜单。
4. **无账号也能长期玩**：存档是本地文件，玩家自己拥有数据。
5. **数据驱动内容**：地图、升级、参数都是数据；加地图不加系统。

### 1.3 非目标

- 不做拟真公交调度（时刻表、票价、司机排班、道路拥堵）。
- 不做剧情、角色、关卡叙事。
- 不做多人、排行榜、UGC 分享（后续可加，不进 MVP）。
- 不复制原作的美术语言、地图轮廓、音效与文案。

## 2. 平台路线：Web 优先，Windows 桌面第二阶段

### 2.1 两阶段定义

| 阶段 | 形态 | 交付物 | 技术 | 进入条件 |
|---|---|---|---|---|
| 阶段一 | Web 浏览器版 | 可在线访问的静态站点；本地存档 + 文件导入导出 | Vite + React + Canvas 2D | 本文件评审通过 |
| 阶段二 | Windows 桌面版 | `.exe`/`.msi` 安装包；真实文件系统存档；可选自动更新 | Tauri 2 外壳 + 复用同一 Web 构建 | 阶段一通过第 12 节全部成熟度门槛 |

**顺序原则：** 阶段二不是重写，而是“换壳 + 换适配层”。玩法内核、渲染、UI、存档 Schema 在阶段一就必须与平台无关；阶段二只新增 `platform/desktop` 与桌面启动入口。

### 2.2 两阶段都要，但主线按 Web 设计

- 所有规则、数值、交互、存档字段先按 Web 约束设计（无本地路径、无系统权限、无后台进程）。
- 桌面端独有能力（真实文件目录、窗口全屏、安装包更新）只通过接口出现，不反向污染玩法。
- 若 Web 性能或触控体验无法达标，不进入桌面阶段，先修 Web。

## 3. 核心循环

### 3.1 单局流程

1. **开局（0–15 秒）**：载入一张地图轮廓，激活 6–8 个初始站点；解锁 2 条线路槽，但**不预画线路**。玩家画好第一条线后，乘客在 8 秒后开始生成；潮汐湾教程前 2 周再额外延迟 10 秒。
2. **铺线**：选择一条空闲线路颜色 → 从站点拖到另一个站点 → 至少 2 站后线路成立，并自动配发 1 列车。线路可继续从任一端点延伸，也可把端点改接至其他站点。
3. **运行**：列车沿线路双向运行，端点折返；停站先下客、再上客；满载后乘客继续排队。
4. **乘客生成**：每个已接入站点按泊松过程生成乘客；乘客形状表示目的地类型；同类型站点任选其一到达即可。
5. **观察与改线**：队列变长、某方向列车满载、某站开始超载计时，玩家通过改线、加车、加车厢、扩站来缓解。
6. **每周结算**：第 7 天结束后暂停，预览新站点，抽 2 张升级卡（第 4/8/12 周为 3 张），选 1 张并指定目标；新站点在下一周开始激活。
7. **失败与重试**：某站队列长度 > 容量并累计 18 秒 → 全局暂停 → 失败面板 → 可用本周开始快照重试、返回标题或导出存档。

### 3.2 玩家每分钟的循环

`看队列 → 判断瓶颈 → 改一条线/加运力 → 观察 10–20 秒 → 再判断`

设计约束：任何一次有效操作（改线、加车、扩站）都应在 3 秒内看到可见变化；否则玩家会失去因果感。

### 3.3 一周的时间结构

- 1 游戏日 = 20 秒（1× 速度）。
- 1 周 = 7 日 = 140 秒。
- 日内高峰：06–09 与 17–20 点生成倍率升高，站点类型会改变目的地权重。
- 周末结算不计入 140 秒，游戏暂停。

## 4. 规则系统

### 4.1 站点

| 类型 | 图形 | 语义 | 生成权重 | 目的地权重（平峰） |
|---|---|---|---|---|
| 居住 residential | 实心圆 | 住宅区 | 1.0 | 0.95 |
| 工作 work | 实心三角 | 办公/产业园 | 1.0 | 1.15 |
| 商业 commercial | 实心方块 | 商业/消费 | 1.1 | 1.0 |
| 休闲 leisure | 实心菱形 | 公园/文体 | 0.8 | 0.85 |

- 站点类型固定，不随升级变化。
- **枢纽（hub）是站点修饰，不是第五种类型**：双环描边，容量 +2，换乘固定惩罚从 5 秒降为 3 秒；全图最多 2 个。
- 初始站点 6–8 个；每周新增 1 个，直到地图上限（14/16/17）。
- 新站点必须落在陆地轮廓内，与既有站点最小距离 100 px；新站出现时显示“待接入”（虚线环）。
- **未接入任何线路的站点不生成乘客**，也不作为其他乘客的目的地；接入后立即恢复。这样避免新站一出现就把玩家拖死。
- 站点容量基础 6；队列硬上限为容量 × 2；超过硬上限的新乘客被丢弃并显示红色“溢出”图标。

### 4.2 乘客

- 生成：每个已接入站点独立泊松过程，速率见第 6 节；目的地类型按权重抽取，**排除本站类型**。
- 目的地是“类型”不是“具体站”：只要到达任一该类型站点即算送达。
- 生成前检查：若当前网络不存在任何可达的同类型站点，则本次不生成（防止无解乘客）。
- 等待队列包含两类人：本站生成的人、在此换乘的人；两者都占容量。
- 乘客没有个人耐心条；压力统一体现在站点超载计时上，避免玩家同时追踪几十个隐藏计时器。
- 送达计数、平均等待、最大队列用于周结算与失败复盘，不做排行榜。

### 4.3 线路

MVP 只有一种线型：**普通双向折线**。

- 一条线路 = 一个有序站点序列，至少 2 站，最多 14 站；不允许重复站点，不允许分支。
- 相邻两站以直线段连接；线路可在非站点处交叉，交叉**不产生换乘**；只有同一站点被多条线经过时才可换乘。
- 列车在线路两端折返，因此每条线路天然双向可乘。
- 解锁线路数：开局 2 条；第 2 周开始免费解锁第 3 条（含 1 列车）；第 4 周起有机会通过升级卡解锁第 4–6 条。全图最多 6 条。
- 跨水线段消耗地图的桥隧额度；额度不足时拒绝连接并提示，额度由地图初始值与“桥隧工程”升级提供。
- 线路颜色固定为 6 色中的一种，不自定义；颜色同时配 1–6 号数字标签，照顾色觉差异。
- 删除线路时，其列车与已加挂车厢回到“待分配”池，不丢失升级资产。

**环线（P1，不进 MVP）：** 首尾相连，列车单向绕行。寻路状态需带方向（见 5.1）；MVP 不实现，避免新手把环线画成死结。

### 4.4 改线成本

改线不消耗货币，只产生**施工时间**。施工期间该线路不接受新乘客，列车运行到下一站后停靠等待；车上乘客不受影响；暂停时施工计时冻结。

| 操作 | 施工时长 | 说明 |
|---|---|---|
| 新建线路（≥2 站） | 1.5 s | 完成后列车从首站发车 |
| 端点追加 1 站 | 2.0 s + 0.4 s × 新增段数 | 常见为 2.4 s |
| 端点改接其他站 | 2.0 s + 0.4 s × 变更段数 | 旧段拆除 + 新段连接 |
| 移除端点 | 2.0 s | 至少保留 2 站 |
| 删除整条线路 | 3.0 s | 列车回收到待分配池 |
| 中段插站 / 重排（P1） | 3.0 s + 0.4 s × 2 | MVP 砍掉，避免触控误操作 |

- 单次施工上限 6 秒；多条线路可同时施工。
- 施工中的线路 chip 显示斜纹与倒计时环；地图上线段显示为虚线。
- 改线可以发生在列车运行中；若列车所在区段被拆除，列车先驶到原下一站，再等待施工结束。
- 施工期间线路沿用旧站序运行、但不接受新乘客；施工结束时切换到新站序。若列车不在新站序上，列车连同车上乘客回位到新站序最近站点（短暂滑动动画），不丢乘客。
- 删除线路同样走 3 秒施工；结束后列车先到下一站清客，乘客进入该站队列，列车与车厢回收到待分配池。

### 4.5 列车

| 项 | 规则 |
|---|---|
| 配发 | 每条线路创建时自动 1 列；升级可得“待分配列车”，拖到线路 chip 上投入 |
| 上限 | 每条线路最多 4 列 |
| 容量 | 基础 6；每级车厢 +4；每条线路最多 3 级车厢（单车最高 18） |
| 速度 | 55 px/s；每次“全线提速”+8%，最多 2 次 |
| 区间耗时 | `距离 / 速度 + 0.4 s`（加减速惩罚） |
| 停站 | `0.8 s + 0.1 s × 上下客人数`，上限 4.0 s；先下后上 |
| 折返 | 开放线到达端点后停站、折返；折返不额外耗时 |
| 发车分布 | 新增列车投放到“发车间隔最大”的端点，尽量均匀分布 |
| 显示 | 车身用线路色；车厢数用分段刻度；满载时显示白色“满”点；下一站方向用车头小箭头 |

- 列车不跨线运营，不支持“临时调车”。
- 列车满载时，站台乘客不重排、不丢失，继续等待下一列。

### 4.6 失败与重试

**唯一失败条件：** 某站 `queue.length > capacity` 时，超载计时按 1× 累加；当队列回到容量以内，计时按 0.6× 回落；累计达到宽限值（基础 18 秒）即失败。宽限值按地图与升级调整：潮汐湾 24 秒、棋盘旧城 18 秒、三河岛 15 秒；升级每级 +5 秒，最多 2 级。

- 超载不是瞬间失败，玩家有 18 秒窗口处理。
- 失败时暂停，镜头聚焦该站，面板显示：站点类型、当前队列、最近 10 秒上客数、涉及线路、三条可执行建议（如“该站仅 1 条线”“17:00 高峰还有 8 秒”“列车全部满载”）。
- 失败面板提供：**重试本周**（从本周开始快照恢复）、返回标题、导出当前存档。
- 每周开始时在本地保存一份“本周快照”（单独 key，不写入导出文件），用于重试；重试次数计入本局统计，但不影响继续游戏。
- 不设“线路断开即失败”“无列车即失败”“资金耗尽”等次要失败条件。

## 5. 寻路与换乘

### 5.1 图模型

内部寻路状态为 **（站点，线路，方向）**：

- 同一站点可属于多条线路，每个“线路 + 方向”是一个可上车状态。
- 乘车边：沿线路向当前方向到下一站，成本 = 区间耗时 + 停站基础耗时。
- 折返边：开放线端点处，方向翻转，成本 0.5 秒；保证列车折返后仍可被正确寻路。
- 换乘边：同一站点内，从任意线路状态切换到另一线路状态，成本 = 换乘固定惩罚 + 下一程期望等待 + 拥堵附加。
- 起点：站点 + 任一线路上车，计入该线期望等待。
- 终点：目的地类型对应的**任意站点**的任意状态；Dijkstra 在第一次弹出任一目标状态时结束。

方向必须进状态，原因是：乘客不能上反方向的车；环线（P1）只有一个绕行方向；只按无向边寻路会产生“路线正确但永远等不到车”的假路径。

### 5.2 成本公式

```text
总成本 = Σ(区间距离 / 车速 + 0.4s + 停站基础 0.8s)
       + 首程期望等待
       + Σ(换乘固定 5s + 下一程期望等待 + 拥堵附加)
```

- 期望等待 = 该线路单方向发车间隔 / 2；发车间隔 = 往返时间 / 该线列车数。1 列车时约等于半圈时间。
- 拥堵附加：换乘站队列 > 容量 50% 时 +6 秒；> 90% 时 +15 秒。
- 最多 3 次换乘；超过 3 次的路径不生成。
- 平手规则：总成本相差 10% 以内时，优先换乘次数少，其次乘车距离短。
- 目的类型存在多个站点时，取总成本最低的那个；不做“固定目的地站”。

### 5.3 选路与重算

- 乘客生成时计算一次路线，路线表示为“线路段序列”，不落地存具体列车。
- 重算触发：线路施工完成、列车增删、乘客到达换乘站、原路线失效；全量重算每 3 秒最多一次（节流）。
- 施工中的线路从寻路图中移除（不可上车）；已在车上的乘客按旧路线到下一站，到站后再重算。
- 迟滞：新路线剩余成本必须比旧路线低 8% 以上才切换（`params.routing.rerouteImprovementRatio=0.08`）；候车乘客在换线完成后重算，车上乘客在下一站重算，避免玩家改线后乘客在两站之间来回横跳。
- 列车上乘客不在区间中重算；到下一站再判断。

### 5.4 上车规则

- 站台乘客只上“当前线路 = 路线下一程线路”且“列车下一站 = 路线下一站”的车；方向不符不上车。
- 若同线路有多列车，选最先到且有剩余容量的；满载则继续排队。
- 到站顺序：先下客（目的地到达或需要换乘），再上客；换乘客进入本站队列并占用容量。
- 若乘客在当前站发现路线失效且无新路线，留在队列，站点显示“无路线”小图标；不会瞬间失败，但会推高该站超载计时。

### 5.5 防卡死清单

| 风险 | 处理 |
|---|---|
| 新站不可达 | 未接入不生成乘客；接入后才参与需求 |
| 唯一目标站不可达 | 目的地按类型匹配，同类型任一站可达即可；生成前做可达性检查 |
| 乘客上反方向车 | 状态含方向；上车校验列车下一站 |
| 改线把列车困在旧线上 | 列车先到原下一站，再停靠等待施工完成 |
| 施工导致线路长期不可用 | 倒计时可见；暂停冻结；单次最多 6 秒 |
| 环线单向导致永远等不到 | 环线 P1 才加入，且寻路状态带方向；MVP 不做 |
| 换乘站无限堆积 | 拥堵附加推高路径成本，引导乘客绕行；超载计时与失败面板兜底 |
| 队列爆炸 | 队列硬上限 2× 容量，超出丢弃并标记“溢出” |

## 6. 数值模型

### 6.1 时间与速度

### 6.2 乘客生成

| 参数 | 键 | 初始值 | 可调范围 | 单位 | 说明 |
|---|---|---|---|---|---|
| 单站基础生成率 | `demand.baseRatePerStation` | 0.05 | 0.035–0.07 | 人/秒 | 第 1 周、标准图 |
| 每周增长 | `demand.weeklyGrowth` | 1.10 | 1.06–1.15 | ×/周 | 乘法增长 |
| 增长软上限 | `demand.growthSoftCapWeek` | 12 | 10–16 | 周 | 之后不再按周增长 |
| 地图需求系数 | `maps.<id>.demandScale` | 0.9 / 1.0 / 1.1 | ±20% | × | 潮汐湾 / 棋盘 / 三河岛 |
| 队列硬上限 | `demand.queueHardCapFactor` | 2 | 1.5–2.5 | ×容量 | 超出丢弃 |

**日时段倍率**（24 小时映射到 20 秒；加权均值 1.008）：

| 时段 | 倍率 |
|---|---|
| 00–06 | 0.6 |
| 06–09 | 1.4 |
| 09–17 | 0.9 |
| 17–20 | 1.6 |
| 20–24 | 1.1 |

每个时段同时带 `destinationPhase`（`offpeak` / `morning` / `evening`），直接驱动目的地权重；实现不得在代码里写死 6/9/17/20 点。

**起点权重：** 居住 1.0、工作 1.0、商业 1.1、休闲 0.8。

**目的地权重：**

| 目的地 | 平峰 | 早高峰 | 晚高峰 |
|---|---|---|---|
| 居住 | 0.95 | 0.70 | 1.50 |
| 工作 | 1.15 | 1.50 | 0.50 |
| 商业 | 1.00 | 1.00 | 1.10 |
| 休闲 | 0.85 | 0.60 | 1.20 |

- 生成速率 = `0.05 × 1.10^(周-1) × 地图系数 × 时段倍率 × 起点类型权重`。
- 目的地从“非本站类型”中按上表权重抽取；商业与休闲在夜间也保持基础权重。
- 同一站点两次生成的间隔按指数分布，避免固定节拍。

### 6.3 标准图需求曲线（棋盘旧城）

| 周 | 站点数 | 单站速率（人/秒） | 总需求（人/分钟） | 典型线路/列车 | 估算运力（人/分钟） | 运力/需求 |
|---|---|---|---|---|---|---|
| 1 | 7 | 0.050 | 21.0 | 2 线 / 2 车 | 25 | 1.2× |
| 3 | 9 | 0.061 | 32.7 | 3 线 / 3 车 | 38 | 1.2× |
| 6 | 12 | 0.081 | 58.0 | 4 线 / 5 车 | 74 | 1.3× |
| 9 | 15 | 0.107 | 106.0 | 5 线 / 7 车 | 132 | 1.2× |
| 12 | 16（上限） | 0.143 | 137.0 | 6 线 / 9 车 | 189 | 1.4× |

- 运力估算：`列车数 × 单车容量 × 2 × 60 / 往返 40 秒 × 满载系数 0.7`，仅用于检查数量级，不作为平衡依据。
- 全局运力故意保持 1.2–1.5× 富余；**压力来自空间分布、换乘站与局部线路不足**，而不是总量破产。这样失败总是可定位、可通过改线解决。
- 设计目标：标准图首次失败中位周数 6–9；潮汐湾 8–11；三河岛 5–7。通过无头批量模拟与真人测试校准。

**线长与时间预算（供平衡与地图设计使用）：**

| 项 | 典型值 | 计算/说明 |
|---|---|---|
| 站点间距 | 100–300 px | 最小 100 px；长跨水段可能到 600 px |
| 单区间行驶 | 2.2–5.9 s | `距离 / 55 + 0.4` |
| 单站停靠 | 0.8–4.0 s | 含上下客，随人数增加 |
| 5 站 4 段单程 | 约 15–30 s | 4 段行驶 + 5 次停靠 |
| 往返 | 约 30–60 s | 单程 × 2 |
| 1 列车发车间隔 | 30–60 s | 往返 / 1 |
| 2 列车发车间隔 | 15–30 s | 往返 / 2 |
| 1 列车期望等待 | 15–30 s | 发车间隔 / 2 |

- 发车间隔按“单方向”理解：同一条线两端的乘客都在等同一列车往返，期望等待用半程间隔估算。
- 线路越长、停站越多，单列车发车间隔越大；这是“加车/提速”升级的直接价值。
- 以上数值是地图设计与参数校准的起点，不写死任何具体地图的实际时长。

### 6.6 升级卡池

| 卡 | 权重 | 效果 | 上限 | 目标选择 |
|---|---|---|---|---|
| 新列车 | 28 | 给选择的线路 +1 列车；默认推荐车最少的线 | 每线 4 列 | 选择线路 |
| 加挂车厢 | 22 | 给选择的线路 +4 容量；默认推荐车厢最少的线 | 每线 3 级 | 选择线路 |
| 站台扩建 | 18 | 选择 2 个站各 +2 容量；默认推荐最挤的两站 | 单站 14 | 选择站点 |
| 新线路 | 12 | 解锁下一色线路槽 | 6 条 | 自动 |
| 桥隧工程 | 10 | +1 跨水桥隧额度 | 6 | 自动 |
| 线路提速 | 6 | 选择的线路 +8% 速度 | 每线 2 级 | 选择线路 |
| 超载宽限 | 4 | 所有站宽限 +5 秒 | 2 级 | 自动 |

JSON 权重键：`newTrain` / `carriage` / `stationExpansion` / `newLine` / `bridge` / `speed` / `grace`。

- 每周抽 2 张不重复卡；第 4/8/12 周抽 3 张，仍只选 1 张。
- 第 2 周线路解锁是固定事件，不占卡位；第 4 周起“新线路”进入卡池。

## 7. 关卡与地图

### 7.1 设计原则

- 逻辑坐标固定 1280×800，渲染等比缩放并留安全边距 80 px。
- 地图轮廓、河流、绿地均为**原创抽象图形**，不使用任何真实城市轮廓，也不使用原作地图布局。
- 水域会影响线路：跨水线段需要消耗地图的桥隧额度；额度由地图初始值和“桥隧工程”升级提供，不是货币费用。额度不足时跨水连接会被拒绝并提示。
- MVP 使用手工摆放的站点锚点与固定激活顺序；程序化生成只用于后续无尽/每日挑战，且复用同一地图 Schema。

### 7.2 三张起步地图

| 地图 | 轮廓 | 起始站 / 上限 | 初始线路 | 桥隧 | 需求系数 | 超载宽限 | 核心差异 | 难度 |
|---|---|---|---|---|---|---|---|---|
| 潮汐湾 Tidal Bay | 半月形海湾 + 两侧伸出的半岛 | 6 / 14 | 2 | 2 | 0.9 | 24 s | 海湾把城市切成两簇，长跨水线路多；教学图 | 新手 |
| 棋盘旧城 Old Grid | 不规则圆角矩形，中间一条窄运河 | 7 / 16 | 2 | 1 | 1.0 | 18 s | 站点密集、运河把旧城切成两半；标准图 | 标准 |
| 三河岛 Three Rivers | 两条河把陆地切成三个叶瓣 | 8 / 17 | 2 | 2 | 1.1 | 15 s | 跨叶瓣必须换乘或桥隧；最容易出现换乘站堆积 | 挑战 |

**初始站点类型配比：**

| 地图 | 居住 | 工作 | 商业 | 休闲 |
|---|---|---|---|---|
| 潮汐湾 | 3 | 1 | 1 | 1 |
| 棋盘旧城 | 2 | 2 | 2 | 1 |
| 三河岛 | 3 | 2 | 2 | 1 |

- 新站按每张地图手工排定的 `appearWeek` 顺序激活，保证前三周的类型组合可控，不会出现“连续 4 个同类型站”。
- 站点锚点之间最小距离 100 px，距轮廓边缘至少 40 px；新站不落在水域。
- 潮汐湾前 2 周需求再乘 0.85，作为教学缓冲；之后恢复正常系数。

### 7.3 地图数据格式

```json
{
  "id": "tidal-bay",
  "name": "潮汐湾",
  "difficulty": "easy",
  "size": { "width": 1280, "height": 800 },
  "outline": "M 120 420 C 180 240, 420 180, 620 260 ... Z",
  "water": ["M 520 0 C 580 220, 760 300, 720 520 ... Z"],
  "parks": ["M 260 520 C 320 500, 360 560, 300 600 Z"],
  "stations": [
    { "id": "s01", "x": 280, "y": 420, "type": "residential", "appearWeek": 1 },
    { "id": "s02", "x": 520, "y": 330, "type": "work", "appearWeek": 1 },
    { "id": "s03", "x": 760, "y": 390, "type": "commercial", "appearWeek": 1 },
    { "id": "s04", "x": 900, "y": 520, "type": "leisure", "appearWeek": 1 }
  ],
  "tuning": {
    "demandScale": 0.9,
    "overloadGraceSec": 24,
    "stationCap": 14
  }
}
```

- `outline`、`water`、`parks` 使用 SVG path 字符串，Canvas 通过 `Path2D` 直接绘制。
- `stations.appearWeek` 决定激活周；第 1 周以外的站点在未激活时不可见。
- 初始线路不预画，由玩家创建；`tuning` 覆盖全局参数。
- 地图文件通过 Schema 校验：至少 6 站、至少 2 种类型、所有点在地图内、`appearWeek` 连续无空洞。

### 7.4 程序化生成（P1，不用于 MVP 三图）

同一 Schema 可由生成器产出，供无尽/每日挑战使用：

1. **轮廓**：以中心为原点取 12 个角度控制点，半径在 280–360 px 间做低频噪声，Catmull-Rom 闭合。
2. **水系**：1–2 条三次贝塞尔曲线切成水域，宽度 60–140 px；跨水线段消耗桥隧额度。
3. **站点点位**：在陆地多边形内做 Poisson Disk 采样，最小间距 100 px，边缘留 40 px。
4. **类型分配**：选 4–6 个类型种子点，其余站点按到种子点的加权距离分配；保证每种类型至少 2 站。
5. **激活顺序**：先取靠近几何中心的 6–8 站作为初始站，其余按“距中心由近到远 + 类型补位”排序，逐周激活。
6. **校验**：所有站在陆地上、间距达标、初始类型≥3 种、前三周每类型至少 1 站；不满足则换种子重试。
7. **存储**：只存 `seed + 生成参数`，运行时重放生成；每日挑战用 UTC 日期派生种子。

程序化地图必须与手工地图走同一套 Schema 与校验，避免出现第二套渲染/规则路径。

## 8. 视觉与声音方向

### 8.1 视觉语言

借鉴“公共交通线路图”的通用视觉语法（粗色线、几何站点、留白、扁平色块），但不复制原作的具体配色、图标、版式与地图。目标是“像一张可玩的城市线路图”，而不是“像 Mini Metro”。

**基础色板（默认浅色）：**

| 用途 | 色值 | 说明 |
|---|---|---|
| 画布底色 | `#F5F2EA` | 暖纸白，长时间不刺眼 |
| 陆地 | `#E9E4D8` | 与底色低对比 |
| 水域 | `#CFE0E3` | 低饱和蓝灰 |
| 绿地 | `#DDE6D2` | 低饱和绿 |
| 主文字/站点 | `#20242B` | 近黑 |
| 次要文字 | `#6B7280` | 灰 |
| 危险/超载 | `#C0392B` | 红色，仅危险状态 |
| 警告 | `#E0A100` | 黄色，队列 50–99% |
| 施工 | `#8A8F98` + 斜纹 | 中性灰 |

**线路色（6 色，Okabe–Ito 风格，色觉友好）：**

| 编号 | 色值 | 名称 |
|---|---|---|
| 1 | `#0072B2` | 蓝 |
| 2 | `#D55E00` | 朱红 |
| 3 | `#009E73` | 青绿 |
| 4 | `#CC79A7` | 品红 |
| 5 | `#E69F00` | 橙黄 |
| 6 | `#56B4E9` | 天蓝 |

- 线路 chip 同时显示编号 1–6；P1 增加“图案辅助”（虚线/点线）开关。
- 站点图形统一用主文字色描边 + 浅色填充；线路颜色只用于线段、列车、线路 chip，不污染站点类型识别。
- 乘客 token 使用目的地类型的缩小实心图形（圆/三角/方/菱），统一墨色，不按线路染色。

**尺寸规范（1280×800 逻辑坐标）：**

| 元素 | 规格 |
|---|---|
| 线路宽度 | 7 px；选中 9 px + 外侧 2 px 浅色光晕 |
| 施工线路 | 7 px 虚线，3 px 间隔，灰 |
| 普通站点 | 半径 10 px，2 px 描边 |
| 枢纽站点 | 外环半径 15 px + 内环 10 px |
| 乘客 token | 半径 4.5 px |
| 队列显示 | 站点下方弧形排列，最多显示 8 个，其余显示 `+N` |
| 列车 | 18×10 px 圆角矩形，按容量等分刻度 |
| 字体 | Inter（OFL）+ 系统中文回退；数字使用等宽数字 |
| 字号 | 正文 14，面板标题 20，周结算 28 |

- 跨水线段自动绘制两条短桥枕线（纯视觉，不产生费用），避免线路像悬浮在水面。
- 站点标签不常驻，悬停/选中时在底栏显示；避免地图文字过密。
- 所有信息不得只靠颜色表达：超载有计时环，满载有“满”点，施工有斜纹与倒计时。

### 8.2 动效节奏

| 事件 | 动效 | 时长 |
|---|---|---|
| 新建线段 | 从起点向终点描画 | 200 ms ease-out |
| 站点激活 | 缩放 0.6→1 + 淡入 | 300 ms |
| 列车到站 | 车头轻微压缩 + 站点脉冲 | 150 ms |
| 上下客 | token 沿弧线移动 | 150 ms/批 |
| 升级卡出现 | 上移 12 px + 淡入 | 250 ms |
| 超载计时 | 站点外环顺时针收缩 | 1 s 循环 |
| 失败 | 聚焦站点，背景降饱和 | 400 ms |

- 不支持屏幕震动；失败不闪屏。
- 提供“减少动态”开关，关闭描画、脉冲与卡片位移。
- 所有动效不影响逻辑时间；暂停时停住。

### 8.3 声音

MVP 以 WebAudio 实时合成为主，避免版权与资源体积问题：

| 事件 | 合成方案 | 音量 | 节流 |
|---|---|---|---|
| 连接站点 | 440 Hz 方波 60 ms + 快速衰减 | 0.25 | 每次操作 |
| 送达乘客 | 880 Hz 三角波 40 ms | 0.15 | 80 ms 内合并 |
| 周结算 | 523→659 Hz 两音琶音 | 0.3 | 每周一次 |
| 超载警告 | 220 Hz 正弦脉冲，1 s 一次 | 0.2 | 仅超载时 |
| 失败 | 220→110 Hz 下滑 | 0.4 | 一次 |

- 首次用户手势后解锁 AudioContext；设置中可分别调 SFX/环境音量并持久化。
- 可选环境底噪：低音量粉噪 + 缓慢滤波，默认关闭。
- 若后续需要更丰富音效，只用 CC0 素材（Kenney UI Audio、freesound 筛选 CC0），并在 `CREDITS.md` 记录来源与许可；不使用原作音乐/音效。
- 音频实现放在平台适配层，内核只发事件，不直接调用 WebAudio。

## 10. 存档系统（Web 与桌面共用）

### 10.1 原则

1. **本地优先**：无账号、无服务器、无云同步；存档默认只在本机。
2. **格式统一**：Web 与 Windows 桌面读写同一套 JSON Schema，可互读。
3. **可导出**：任何时候都能导出单文件，换设备靠文件迁移。
4. **可恢复**：自动存档 + 导入前备份 + 版本迁移；坏档不覆盖好档。
5. **内核不碰 IO**：序列化/校验/迁移是纯函数；读写由平台适配层完成。

### 10.2 存档文件结构

顶层字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `schemaVersion` | number | 固定从 1 开始；迁移依据 |
| `appVersion` | string | 生成该档的版本，仅诊断 |
| `savedAt` | string | ISO 8601 带时区，仅展示 |
| `source` | `"web"` / `"desktop"` | 诊断用，读取时忽略 |
| `slot` | number | 1–3，导入时可重映射 |
| `settings` | object | 音量、速度、减少动态等，随档迁移 |
| `sim` | object | 完整可重放模拟状态 |

`sim` 关键字段：

| 字段 | 说明 |
|---|---|
| `seed` | 本局种子，创建后不变 |
| `rngState` | 4 个 uint32，保存时精确快照 |
| `tick` | 60 Hz 逻辑步数；恢复后从下一 tick 继续 |
| `week` / `dayIndex` / `dayProgress` | 时钟位置；`dayIndex` 0–6 |
| `paused` / `speed` | 恢复时保持暂停，避免读档即失败 |
| `mapId` | 地图 |
| `stations` | 坐标、类型、容量、队列、超载秒数、是否接入、激活周、下次生成 tick |
| `lines` | 颜色索引、站点序列、施工状态（`{ endTick, newStationIds, changedSegments }`，空为无施工） |
| `trains` | 所属线路、方向、当前区间与进度、容量、车上乘客（只存目的地类型） |
| `pendingTrains` / `pendingCarriages` | 待分配升级资产 |
| `pendingUpgrade` | 周结算未完成时的卡牌与选择状态 |
| `newStationId` | 下周待激活站点（可空） |
| `tutorial` | 已看提示、是否完成 |
| `stats` | 送达、生成、重试次数、游玩秒数 |

**不保存的派生数据：** 乘客路线（读档后按当前网络重算）、动画状态、Canvas 尺寸、任何绝对文件路径、渲染缓存。

### 10.4 存储位置与命名约定

**存档命名约定（已定）：**

- 存档文件：`linevale-save-slot{slot}-v{schemaVersion}.json`；当前示例 `linevale-save-slot1-v1.json`。
- 本周快照：`linevale-retry-slot{slot}.json`，仅本地，不导出。
- 设置：`linevale-settings.json`；本机最佳记录：`linevale-profile.json`。
- 备份：`linevale-save-slot{slot}-v{schemaVersion}.backup-{timestamp}.json`。
- 导入接受任意 `.json` 文件名，实际以文件内 `schemaVersion` 与 `slot` 为准；文件名只是约定。
- 桌面读取槽位时优先当前 `v{current}`；找不到再扫描同槽位旧版本，迁移后写入当前版本，旧文件保留为备份。

**Web：**

| 内容 | 键/位置 |
|---|---|
| 设置 | `localStorage["linevale.settings"]` |
| 存档槽 1–3 | `localStorage["linevale.save.slot1"]` … `.3` |
| 本周快照 | `localStorage["linevale.retry.slot1"]` … `.3`（不导出） |
| 本机最佳记录 | `localStorage["linevale.profile"]`（周数、送达数、地图） |

- Web 槽位是键，不是文件；导出时才按上面的文件命名生成。
- 自动存档触发：每 15 秒、每周结算、暂停、页面隐藏、导出前。
- 自动存档失败（配额/隐私模式）时顶栏显示持续警告，并提示“请导出存档”。
- 单档约 30–60 KB，3 槽远低于 5 MB 配额；不存历史回放。

**Windows 桌面（阶段二）：**

| 内容 | 位置 |
|---|---|
| 存档槽 | `%APPDATA%\Linevale\saves\linevale-save-slot{slot}-v1.json`（slot = 1–3） |
| 设置 | `%APPDATA%\Linevale\linevale-settings.json` |
| 本周快照 | `%APPDATA%\Linevale\retry\linevale-retry-slot{slot}.json`（slot = 1–3） |
| 本机最佳记录 | `%APPDATA%\Linevale\linevale-profile.json` |
| 导出 | 用户通过系统保存对话框选择任意目录，默认文件名按上述约定 |

- 桌面端不使用 localStorage 存主存档；真实文件便于备份、查看、手动替换。
- 写入采用“临时文件 + 重命名”原子操作；导入前把当前槽复制为 `linevale-save-slot{slot}-v{schemaVersion}.backup-{timestamp}.json`。

### 10.5 导出 / 导入流程

**导出（两端一致）：**

1. 暂停并立即写一次自动存档。
2. 序列化 `SaveFileV1`，格式化 2 空格缩进，便于人工检查。
3. 文件名：`linevale-save-slot{slot}-v{schemaVersion}.json`（例：`linevale-save-slot1-v1.json`）；导入不依赖文件名。
4. Web 用 Blob + `<a download>`；桌面用保存对话框 + 文件写入。
5. 成功后 toast 显示“已导出，建议放到网盘或发给自己”。

**导入（两端一致）：**

1. 选择文件（Web 文件选择/拖入；桌面系统打开对话框）。
2. 校验：大小 ≤ 2 MB；JSON 可解析；`schemaVersion` 存在且 ≤ 当前支持版本；Schema 校验必填字段与数值范围。
3. 版本迁移：`v1 → v2 → …` 纯函数链；任何一步失败则拒绝。
4. 预览：地图、周数、游玩时长、送达数、保存时间。
5. 选择目标槽（1–3），确认覆盖；先备份当前槽，再写入。
6. 写完后保持暂停，提示“导入成功，可继续”。
7. 失败提示必须具体：文件不是存档 / 版本过新 / 字段损坏 / 槽位写入失败；绝不静默覆盖。

### 10.6 换设备不丢档的完整路径

1. 旧设备：暂停 → 顶栏“存档” → “导出当前进度” → 得到 JSON 文件。
2. 把文件放到网盘、U 盘或发给自己（任选其一，不需要账号绑定）。
3. 新设备：打开游戏 → 标题页“导入存档” → 选文件 → 预览 → 选槽位 → 确认。
4. 新设备自动存档开始写入本地槽位；建议立刻再导出一次作为备份。
5. 桌面版同流程，只是导入来源变成系统文件对话框，落盘位置为 `%APPDATA%\Linevale\saves`。

**边界说明：** 浏览器清空站点数据/隐私模式会删除本地槽位，因此“导出文件”是唯一可靠的跨设备与长期备份；MVP 不提供云同步。

### 10.7 版本与安全

- `schemaVersion` 只增不减；废弃字段不删除，先标记可选。
- 迁移函数放 `game/save/migrate.ts`，纯函数、无 IO、可单测；每个历史版本保留固定 fixture。
- 导入是唯一的外部输入边界：限制大小、校验类型与范围、不使用 `eval`、不执行文件内任何字符串。
- 存档不含个人信息、不含账号、不含设备路径；`source` 与 `savedAt` 仅诊断。
- 失败重试快照与主存档分离，避免导出文件体积翻倍；快照损坏不影响主档。

## 11. 技术选型与平台抽象层

### 11.1 Web 技术栈

| 层 | 选择 | 理由 | 不选什么 |
|---|---|---|---|
| 语言 | TypeScript 5.x（`strict`） | 状态机与存档 Schema 需要类型约束；重构安全 | 纯 JS |
| 构建 | Vite 6 | 启动快、静态产物简单、Tauri 直接复用 `dist` | Webpack（配置重） |
| UI | React 18 | 只做 HUD、弹窗、菜单；生态成熟 | 用 React 驱动游戏循环 |
| 渲染 | Canvas 2D（`Path2D` + DPR 缩放） | 同时存在列车、乘客 token、队列、动效；Canvas 比 SVG 少 DOM 开销；本作图元 < 500，无需 Pixi | SVG（节点多时掉帧）、Pixi/Phaser（为本作过重） |
| 状态 | 游戏内核普通 TS 对象 + Zustand 管 UI 状态 | 内核可变对象便于 60 Hz 更新；React 只订阅 10 Hz 快照，避免每帧重渲染 | 把整个模拟放进 React state |
| 随机 | sfc32（4×uint32 状态） | 可保存/恢复、跨平台一致、足够快 | `Math.random`（不可复现） |
| 校验 | zod | 导入存档是外部输入，需要运行时校验；体积可接受 | 手写校验（易漏） |
| 测试 | Vitest + 可选 Playwright | 寻路/超载/存档迁移适合纯函数测试；浏览器冒烟用 Playwright | 只靠手测 |
| 音频 | WebAudio 实时合成 | 无版权、零资源体积、跨平台一致 | 引入大型音频库 |
| 部署 | 静态托管（Cloudflare Pages / GitHub Pages 任选） | 无后端、无账号、成本低 | 自建服务器 |
| 桌面 | Tauri 2 | 见 11.5 | Electron（降级方案） |

**循环与确定性：**

- `requestAnimationFrame` 驱动，固定逻辑步长 1/60 秒，累加器最多补 5 步，防止切后台后爆炸。
- 渲染用插值 alpha，逻辑不受帧率影响。
- 速度倍率只乘模拟时间，不改变 tick 频率。
- 内核禁止使用 `Math.random`、`Date.now`、`localStorage`、`window`；所有随机走注入的 RNG，所有计时走 tick。
- 存档只在暂停/tick 边界写入，避免半帧状态。

**画布与 UI 分工：**

- 地图、线路、站点、列车、乘客、超载环、施工虚线全部 Canvas。
- 顶栏、线路 chip、周结算卡、设置、存档面板、失败面板用 DOM/React，便于排版、滚动、无障碍与输入。
- 命中测试用“站点/线路 chip 的圆形与矩形包围盒”，站点数量 ≤ 17，不需要空间索引。

### 11.2 分层与依赖方向

```text
app（启动、页面编排）
 ├─ ui（React 组件）        ─┐
 ├─ render（Canvas 渲染）   ─┼─ 只依赖 game 的类型与只读数据
 ├─ platform 接口 ← web/desktop 适配器
 └─ game（纯玩法内核 + 存档编解码 + 地图数据）
```

- `game/` 是唯一的规则真相：模拟、寻路、生成、升级、存档 Schema/迁移、参数。
- `render/` 只读模拟状态并画图，不修改规则；可做纯视觉插值。
- `ui/` 通过注入的 `Platform` 与 `GameController` 交互，不直接碰 localStorage/文件。
- `platform/` 只做 IO 与系统能力；不包含玩法。
- `app/` 是组合根，决定用 Web 还是 Desktop 适配器。

**强制约束：**

- ESLint `no-restricted-imports` 禁止 `game/**` 导入 `platform/**`、`ui/**`、`render/**`、`react`。
- CI 增加一条“内核纯净检查”：`game/` 下不得出现 `window`、`document`、`localStorage`、`fs`、`path`、`Math.random`、`Date.now` 字符串（测试文件除外）。
- 存档编解码可在 Node 里跑：CI 用纯字符串输入输出验证，不依赖浏览器。

### 11.3 平台接口（建议签名）

```ts
// platform/types.ts
export interface SaveSlotSummary {
  slot: number;
  mapId: string;
  week: number;
  savedAt: string;
  playTimeSec: number;
}

export interface SaveRepository {
  list(): Promise<SaveSlotSummary[]>;
  read(slot: number): Promise<string | null>;   // 原始 JSON，校验在 game/save
  write(slot: number, json: string): Promise<void>;
  remove(slot: number): Promise<void>;
  backup(slot: number): Promise<void>;
}

export interface FileBridge {
  exportFile(suggestedName: string, contents: string): Promise<void>;
  importFile(): Promise<{ name: string; contents: string } | null>;
}

export interface WindowBridge {
  setFullscreen(on: boolean): Promise<void>;
  isFullscreen(): Promise<boolean>;
}

export interface AudioBridge {
  unlock(): Promise<void>;
  play(event: AudioEvent): void;
  setVolumes(sfx: number, ambience: number): void;
}

export interface LifecycleBridge {
  onHidden(cb: () => void): () => void;
  onQuitRequested(cb: () => void): () => void;
}

export interface Platform {
  saves: SaveRepository;
  files: FileBridge;
  window: WindowBridge;
  audio: AudioBridge;
  lifecycle: LifecycleBridge;
  now(): number; // 仅用于 savedAt 等元数据，不用于模拟
}
```

- 适配器返回**原始字符串**，存档校验/迁移在 `game/save` 内完成，确保两端 Schema 完全一致。
- 平台接口不暴露文件路径、不暴露 Node/Rust 类型，UI 无感知。

### 11.4 平台能力边界

| 能力 | 归属 | Web 实现 | Desktop 实现 | 内核是否感知 |
|---|---|---|---|---|
| 玩法模拟、寻路、升级、失败判定 | 平台无关 | 同一份 `game/` | 同一份 `game/` | 是（唯一真相） |
| 地图数据、参数、RNG | 平台无关 | 同一份 | 同一份 | 是 |
| 游戏状态（时钟、队列、线路、列车、升级） | 平台无关 | 同一份 `game/` | 同一份 `game/` | 是 |
| 存档 Schema、序列化、迁移 | 平台无关 | `game/save` | `game/save` | 是 |
| 渲染 | 平台无关 | Canvas 2D | Canvas 2D（WebView2） | 否 |
| UI | 平台无关 | React DOM | React DOM | 否 |
| 存档槽读写 | 平台适配 | localStorage | `%APPDATA%` 文件 | 否 |
| 导入/导出文件 | 平台适配 | Blob 下载 + `<input type=file>` | 系统对话框 + fs | 否 |
| 窗口/全屏 | 平台适配 | Fullscreen API | Tauri window API | 否 |
| 声音播放 | 平台适配 | WebAudio | WebAudio | 否 |
| 生命周期（隐藏/退出） | 平台适配 | `visibilitychange` / `beforeunload` | Tauri close 事件 | 否 |
| 自动更新 | 平台适配（P2） | 静态版本检查 | Tauri updater | 否 |

**结论：** 阶段二需要改的只有 `platform/desktop/*`、`main.desktop.ts`、`src-tauri/` 与打包配置；`game/`、`render/`、`ui/`、`app/screens` 不改。

### 11.5 Electron vs Tauri（明确推荐 Tauri 2）

| 维度 | Electron | Tauri 2 | 对本项目的含义 |
|---|---|---|---|
| 与 Web 代码复用 | 很高，约 95–100%（同一份前端，需 preload/IPC） | 很高，约 95–100%（同一份 `dist`，通过 JS API/插件） | 两者都能复用；Tauri 的薄壳更少胶水 |
| 安装包体积 | 约 80–150 MB | 约 5–12 MB（依赖系统 WebView2） | 小游戏不应背 100 MB 运行时 |
| 本地文件存档 | Node `fs`，JS 直接读写，最顺 | 官方 fs/dialog 插件，能力白名单，稍多配置 | 两者都满足；Tauri 更安全、路径权限更清晰 |
| 运行时内存 | 较高（自带 Chromium） | 较低（共享 WebView2） | 长时间挂着玩更友好 |
| 开发工具链 | 只需 Node | Node + Rust + MSVC Build Tools | Tauri 的主要成本；只影响构建，不影响玩家 |
| 打包/更新 | electron-builder + updater，成熟但包大 | Tauri bundler + 签名 updater，包小 | Tauri 安装/下载成本更低 |
| 安全边界 | 需手动收紧 IPC/Node 集成 | capability 白名单默认更窄 | Tauri 更适合“只读写自己的存档” |
| 生态/资料 | 最成熟 | 较新但官方插件覆盖本作所需 | 本项目需求简单，Tauri 足够 |

**推荐：Tauri 2。** 理由按本项目权重排序：

1. 这是离线单机小游戏，安装包 5–12 MB 比 100 MB 更合理，分发/更新成本低。
2. 只需要“存档文件读写 + 文件对话框 + 全屏 + 可选更新”，Tauri 官方插件全覆盖，不必写复杂原生代码。
3. 权限模型更窄，适合只访问 `%APPDATA%\Linevale` 的存档目录。
4. WebView2 在 Windows 10/11 通常已存在；缺失时安装器可带 bootstrapper。

**唯一明确的代价：** 构建机需要 Rust + MSVC。缓解方式：阶段二第一步先做“Tauri 空壳打包”技术验证；若本机环境无法配置或维护成本不可接受，再降级 Electron。由于平台接口已隔离，降级只改 `platform/desktop` 实现与打包脚本，不改内核。

**明确不推荐 Electron 作为首选**，但不是禁止：只有在“完全不想安装 Rust 工具链”时才选 Electron。

运行时说明：玩家端都不需要安装 Node 或 Rust；Electron 自带 Chromium，Tauri 依赖系统 WebView2。开发机两者都需要 Node，Tauri 额外需要 Rust + MSVC Build Tools。

### 11.7 桌面打包与更新（阶段二）

## 12. “相对成熟”门槛：何时进入桌面阶段

进入阶段二前，阶段一必须**全部**满足以下 5 条；任一条不达标，继续留在 Web 调优。

| 编号 | 门槛 | 可验收标准 | 验证方式 |
|---|---|---|---|
| G1 核心稳定 | 核心循环无崩溃、无软锁 | 连续 20 局或 60 分钟自动/人工运行，0 崩溃、0 卡死；失败必触发且原因正确；2× 速度下 FPS ≥ 55（1920×1080 集显）；30 分钟内存增长 < 10% | 自动脚本 + 浏览器性能面板 + 人工长跑 |
| G2 内容与平衡 | 三张地图可完整通关/可玩到第 8 周 | 三图均可玩到第 8 周以上；标准图首次失败中位周数 6–9；难度顺序稳定；≥5 名首次玩家中 ≥80% 不看外部说明完成教程 | 20 局以上记录 + 5 人可用性测试 |
| G3 存档可靠 | 导出/导入/恢复不丢档 | 100 次“导出→清空→导入”后，忽略 `savedAt`/`slot`/`source` 的归一化 JSON 完全一致；刷新页面能恢复；非法文件不覆盖原槽；v1 迁移 fixture 全通过；Chrome/Edge/Firefox 均通过 | 自动 round-trip 测试 + 三浏览器手测 |
| G4 交互与性能 | 鼠标与触控都能完成全部核心操作 | 画线、改线、删线、指派列车、选升级、暂停、导出/导入均可在鼠标与触控完成；UI 文案全部来自语言字典且扫描零中文硬编码；无控制台错误；减少动态/色觉辅助可用；1024×640 不遮挡关键 UI | 真机触控 + 响应式检查 + i18n 扫描 + 无障碍抽查 |
| G5 可移植预检 | 内核与存档已与平台解耦 | `game/`、`render/` 零平台导入（CI 通过）；存档 codec 在 Node 无浏览器环境跑通；桌面空壳能加载 Web 导出存档并原样回写；Schema 无绝对路径/平台字段 | ESLint/CI + Node 测试 + Tauri 空壳 spike |

**门槛的意义：** G5 不是“桌面做完了”，而是证明“桌面只需要适配层”。G1–G4 保证玩家在 Web 已经玩得下去，不会把未稳定的玩法带进安装包。

G5 中的“Tauri 空壳”只做一次最小技术验证（能启动、能读写一个测试存档），可在 M7 进行；它不等于启动阶段二，通过后才正式进入 P2。

### 13.1 MVP（Web v0.1）必做

### 13.2 MVP 明确砍掉

| 砍掉项 | 原因 | 去向 |
|---|---|---|
| 环线 | 单向列车会让寻路与新手理解复杂一倍 | P1 |

| 地图目标 / 奖牌 | 目标设计会反过来影响三图平衡 | P1 |
| 地图编辑器 / 种子分享 | 内容生产工具，非玩法必需 | P2/P3 |
| 账号、云同步 | 与“换设备不丢档”的本地文件方案冲突且增加成本 | 永不 |
| 排行榜、联机 | 单机非商业，无服务器 | 永不 |
| 成就、回放 | 不影响核心循环 | P2 |
| 深色主题、英文、线路图案 | 打磨项，不影响可玩性 | P1 |
| 撤销改线 | MVP 用低成本施工 + 本周重试兜底 | P1 |
| 移动原生 App | Web 已覆盖手机浏览器 | 永不 |

### 15.3 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 玩家看不懂乘客为什么不上车 | 觉得规则不公平 | 列车显示下一站与方向箭头；站点面板显示各目的地队列；失败面板给原因；开发者模式有寻路调试层 |
| 换乘站反复堆积、局部必死 | 挫败 | 拥堵附加引导绕行；枢纽卡；本周快照重试；失败建议具体到站 |
| 数值平衡耗时 | 拖慢 MVP | 参数全部外置 JSON；无头批量模拟；先锁“首次失败 6–9 周”一个指标 |
| 三图同质 | 内容不耐玩 | 用地理结构制造差异（海湾/方格/河岛），而不是只改需求系数 |
| 存档损坏/浏览器清数据 | 丢档 | Schema 校验、导入前备份、原子写、持续导出提醒；桌面版真实文件 |
| Canvas 低端设备掉帧 | 体验差 | 队列只画前 8 个 + `+N`；控制 token 数量；2× 目标 55 FPS；必要时降动效 |
| Tauri 工具链配置失败 | 桌面期卡住 | 先做空壳 spike；失败则 Electron 降级，适配层不变 |
| 名称/美术侵权 | 无法发布 | 第 14 节清单；只用原创/CC0；发布前商标检索 |
| 范围蔓延 | 做不完 | 第 13.2 节砍掉项为硬边界；新增需求必须换出等量 MVP 项 |

## 附录 B：术语

| 术语 | 含义 |
|---|---|
| 广义时间 | 乘车时间 + 期望等待 + 换乘惩罚 + 拥堵附加的合计成本 |
| 队列 | 站点上等待上车的乘客集合，含本站生成与换乘乘客 |
| 超载 | 队列长度 > 站点容量；不是瞬间失败，有宽限计时 |
| 施工 | 线路编辑后的不可上车状态，持续 1.5–6 秒 |
| 本周快照 | 每周开始时保存的本地状态，仅用于失败后重试，不进导出文件 |
| 平台适配层 | 只负责存档 IO、文件、窗口、声音、生命周期的薄层 |
| 玩法内核 | `game/` 下与平台无关的规则、状态、寻路、参数、存档编解码 |
